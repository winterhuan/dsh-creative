# 小说工坊：聚焦重设计

[English](2026-10-04-novel-studio-plan.md) | 中文

## 摘要

工作台应扩展现有的 `@winterhuan/dsh-story`，而不是再引入一个小说插件。产品单元是一个作品上的有界任务，不是协作模式、规划方式和执行引擎的矩阵。每个任务明确自己只能讨论、生成候选，还是提交获授权的修改；规划深度按需选择；会话、模型、工具和取消仍由 DSH 负责。

本设计保留前一版方案的有效部分——作品独立于聊天、有来源的上下文、可比较的候选、版本检查和可恢复执行——但删除九种面向用户的组合、preset 切换和重复的 Team 组合。同时增加小说引擎，负责设定圣经、状态账本、上下文组装和质量流程；这些是小说领域资产，不是 DSH 运行时状态。第一阶段只要求跑通一条闭环：选择作品、预览上下文、生成候选、审阅、提交或丢弃，并能安全恢复。

<a id="architecture"></a>
## 架构

即使第一版把它们放在同一个 TypeScript 包中，也保留三个概念层。小说引擎拥有持久的故事语义；DSH 适配层把原生运行能力转换成任务工具；工作台呈现作者决定和产物。

| 层 | 负责 | 不负责 |
|---|---|---|
| 小说引擎 | 设定圣经、细纲、账本、上下文选择、工作流状态和一致性检查 | DSH Session 内部、模型选择或浏览器状态 |
| DSH 适配层 | Skill 与工具注册、限定文件访问、subagent/workflow 调用和运行事件映射 | 权威故事事实或仅属于界面的草稿状态 |
| 工作台 | 作品导航、编辑器、任务抽屉、候选比较和人工批准 | 第二个聊天、隐藏权限或第二个事实来源 |

本仓库中的引擎应使用 TypeScript，并通过文件、任务输入和运行事件接口工作，而不是导入 DSH 实现细节。未来 CLI 或 SDK 可以复用同一引擎。DSH 公共 API 变化时，原则上只需要修改适配层。

<a id="one-core-two-wings"></a>
## 一核两翼

长篇和短篇共享平台与质量层，但不共享写作流水线。项目模式写在 `novel.yaml` 中；`AGENTS.md` 可以补充人和模型的指导，但不是机器可读的模式状态来源。

| 领域 | 共享核心 | 长篇分支 | 短篇分支 |
|---|---|---|---|
| 作品单位 | 文件、候选、版本检查、任务授权和提交报告 | 章节与场景 | 一篇完整故事 |
| 领域状态 | 设定圣经、作者声音、来源记录和审稿记录 | 卷、章卡、滚动摘要、人物知情状态和伏笔账本 | 故事核、情绪与反转设计卡、铺垫证据和结尾目标 |
| 上下文 | 显式来源优先、有界预览和来源版本 | 当前章、邻接正文、相关账本和摘要 | 能容纳时使用全文，加设计卡和文风样本 |
| 质量重点 | 一致性检查、独立审稿、修订上限、反模式信号和人工批准 | 连续性、状态变化、承诺欠账、节奏和连载停靠点 | 开头抓力、铺垫公平、情绪曲线、反转兑现、冗余和结尾画面 |
| 成本策略 | 可见预算和模型路由 | 按章控制成本并保留可恢复状态 | 把更多预算用于整篇通读和修订 |

模式只选择 schema 和 workflow，不悄悄改变作者权限。未来可以通过明确的转换复制共享材料到另一分支，但短篇不能当成章节批次，长篇也不能被强制一次性装入全部上下文。

<a id="design-decision"></a>
## 设计结论

使用一个小说插件、一个普通写作会话和一份任务契约。不把协作模式做成 preset，也不要求作者在说明写作目标前先选择执行引擎。

| 决策 | 采用方案 | 理由 |
|---|---|---|
| 产品边界 | 扩展 `@winterhuan/dsh-story` 及现有工作台 | 现有发现、编辑器、文件跳转和版本写入已经构成合适的宿主 |
| 作者控制 | 按任务授权写入：讨论、候选、提交或有界运行 | 副作用发生的位置就能看到权限 |
| 规划 | 开放探索、当前单元规划或全书地图；有用时才选 | 规划深度不改变谁拥有正文 |
| 执行 | 默认主会话；只有明确要求有界多步运行时才用原生 workflow | 执行机制与任务规模相称 |
| 持久化 | Markdown/TXT 仍是事实来源；结构化小说产物和小型项目索引保存领域状态与任务引用 | 作品可检查、可迁移，不复制 DSH 历史 |
| Team | 后续按需用于长期资料或结构工作 | 成员协作是执行优化，不是写作模式 |

作者只看到三个常用动作：讨论、生成候选和应用指定修改。“续写”是带目标和停笔点的有界任务，不是自主模式。审查服务只返回证据和建议，不能悄悄获得写入权限。

设计明确放弃 preset 热切换、自动全书分析、固定章节配额、强制审查闸门、按分数验收和并行写手团队。这些机制增加状态与成本，却没有保护核心的作者决定。引擎仍然负责真正的领域检查；减少的是过早暴露的产品选择，不是小说领域的严谨性。

<a id="author-journey"></a>
## 作者路径

每个任务都走同一条短路径。界面可以跳过没有工作的步骤，但必须保持相同的状态和授权语义。

1. 选择作品和目标：场景、文档、章节范围或问题。
2. 选择意图：讨论、生成候选、应用修改或在有界范围内续写。
3. 预览上下文：所选文件、版本、选段、缺失和未决选择。
4. 在现有 DSH 会话中执行；只有任务明确要求时才增加原生 subagent 或 workflow。
5. 将结果归为讨论、候选、已提交文档、等待作者决定，或保留产物的失败。
6. 作者采纳、编辑、丢弃或恢复。作者采纳或明确授权提交前，候选不得改变正文。

| 请求 | 默认结果 | 停止条件 |
|---|---|---|
|“帮我找出冲突”| 在聊天中返回证据和选项 | 缺少来源或作者决定未定 |
|“试写这个场景”| 绑定源版本的候选稿 | 候选就绪或上下文不足 |
|“改写这段选文”| 候选差异 | 源版本变化或选区不明确 |
|“写下一章”| 一次有界提交；若先要求审阅则生成候选 | 达到目标、冲突、错误或出现重大选择 |
|“写三章”| 每章一个检查点的串行有界运行 | 任一章失败，后续章节不启动 |

已有稿件仍是一等输入。接入流程预览编码和章节映射、保留源文件，并让作者从选定任务开始；不要求先完成全书分析。

<a id="work-and-task-model"></a>
## 作品与任务模型

作品是文件、草稿、候选、任务和 DSH 会话共享的稳定身份。文件继续使用普通 Markdown 或 TXT，作者离开工作台后仍能访问正文。

| 记录 | 必需字段 | 所有者与规则 |
|---|---|---|
| 作品索引 | 根目录、文档、顺序、可选标题和写作偏好 | 作品服务；显式保存时才延迟创建，缺失值从文件推导 |
| 设定圣经 | 世界规则、人物卡、文风样本和读者承诺 | 小说引擎；需要检查的部分结构化，需要作者理解的部分保留 prose |
| 细纲 | 全书方向、剧情弧目标和当前单元 beat | 小说引擎；作者确认前始终是提案 |
| 账本 | 时间线、人物状态、信息边界、伏笔和新增事实 | 小说引擎；每条记录带来源版本、状态和来源记录 |
| 任务 | 意图、目标、基础版本、上下文选择、预算和停笔点 | 任务服务；启动后不可变，取消状态除外 |
| 候选稿 | 源文档、基础版本、选区或整文档补丁、内容和诊断 | 作品服务；采纳前不得成为当前正文 |
| 交接记录 | 已完成范围、实际版本、未决选择和原生任务引用 | 作品服务；简短且有来源，不复制聊天 |
| 历史 | 旧文档版本和操作元数据 | 作品服务；恢复会创建新版本并保留后续历史 |

影响后续写作的事实必须指向文档版本或作者确认的设定。模型提取的事实在配置的提交步骤确认前只能作为账本提案；提取失败不能阻止有效正文提交。派生记录可能因源文档失效；界面将其标为待复核，不把它们当作事实。第一版不要求逐句依赖图或向量数据库。

上下文按以下顺序组装：当前请求和显式约束、作者选定材料、目标文本及邻接段落、相关设定与规划、相关历史。预览属于任务记录，因此缺失或截断的必需来源可见且可恢复。

所有写入都对准确的基础版本执行比较并交换。源文本变化时拒绝旧候选或要求重新比较。章节流程是规划 → 场景草稿 → 审稿 → 有界修订 → 正文提交 → 账本提案与摘要。账本更新单独记录，因此记账失败不能假装正文没有提交。跨文档运行逐项报告结果，不能声称整本书原子回滚。

<a id="quality-loop"></a>
## 质量闭环

把一致性、追读力和文字质感当成三个不同问题，并为它们使用不同证据。引擎不能把文学代理指标伪装成客观批准分数。

| 问题 | 主要证据 | 作用 |
|---|---|---|
| 本章是否自洽？ | 用代码检查身份、时间、地点、状态、知情边界、已登记实体和有来源的账本变化 | 阻断硬冲突；报告较软的警告 |
| 本章是否让人想继续读？ | 场景卡字段、承诺与回收记录、状态变化检查、独立审稿和小规模人工试读 | 标记缺少欲望、阻碍、变化或读者价值；由作者决定是否修改 |
| 文字是否像这部作品？ | 文风样章、对白声音检查、重复与句式信号、作者或读者盲评比较 | 建议定点重写；不自动证明“像人”或“好” |

章节按场景逐个写入。每个场景记录目标、阻碍、结果以及情绪或信息变化。审稿员只接收正文和相关来源产物，不接收写手隐藏的推理过程，并返回位置和可执行意见。修订有可见上限；无法解决的分歧交给作者，不再静默循环。

第一版把设定圣经和账本保存为可检查的文件。只有测得检索压力后才增加派生索引；SQLite、向量嵌入和 Git 提交都是集成选项，不是权威事实来源。即使 DSH 不可用，文件事务和版本记录也必须足以恢复作品。

<a id="long-and-short-pipelines"></a>
## 长篇与短篇流水线

长篇分支使用章卡和场景卡。卡片记录目标、阻碍、结果、状态变化、场景节拍、知情边界、伏笔变化、章末钩子和可选的平台字数范围。没有有意义的状态变化时，按项目策略给出警告或停止，不把它当成普遍的文学定律。

它的常规路径是：装配有界上下文 → 逐场景起草 → 运行硬一致性检查 → 独立审稿 → 有界修订 → 反模式和声音检查 → 提交章节及账本提案 → 人工抽查。长篇批次保持串行，因为下一章依赖上一章已提交的状态。

短篇分支使用一张设计卡，包含故事核、读者承诺、主角欲望与创伤、开头钩子、反转类型和揭示位置、铺垫证据、情绪曲线、结尾画面和规模限制。它的常规路径是：市场或参考分析 → 故事核 → 作者批准设计卡 → 节拍与字数预算 → 起草 → 铺垫回溯 → 整篇读者视角审稿 → 整篇修订 → 反模式及标题/开头检查 → 人工定稿。

短篇检查必须在正文中定位每条设计铺垫，测试揭示是否公平但不明显，找出情绪平坦区，删除既不服务情绪也不带来故事变化的场景，并检查结尾画面是否落成解释性总结。这些检查补充共享质量层，不能把固定公式变成保证。

<a id="native-dsh-composition"></a>
## 原生 DSH 组合

继续使用现有 story bundle 作为安装边界。在该包内增加小说引擎模块和薄的 DSH 适配层；不要创建 `novel-studio`、三个协作 preset 或 Team 专用插件行。业务代码通过适配接口工作，不直接依赖 DSH 内部 store 或 Cordis 服务。

普通路径使用当前 Session、Skill 加载和原生文件工具。有界续写可以调用现有原生 `workflow`，由任务脚本声明目标、预算、写入策略和检查点。subagent 可以读取或分析；除非父任务明确授权且运行时确实执行，该 subagent 不拥有正文写入权限。可以增加规划、写作、审稿和记账等专家角色，但角色不能替代工具级权限检查。

插件必须通过测试确认原生委派的边界，不能凭推测。重点核对父子任务取消、shell 和 workflow 子会话的写入路径，以及提交失败后报告的终态。Role 文案只是指导；持久边界由作品服务和工具组合执行。

不需要实时切换 preset。任务启动时记录当前 Session 和作品版本。写作偏好的变化影响下一任务；运行中的任务必须先取消并核实终态。

<a id="workbench-and-task-states"></a>
## 工作台与任务状态

保留现有编辑器和文件树。增加紧凑的任务抽屉，不再建立第二个聊天或模式向导。

抽屉显示作品、目标、意图、上下文预览、写入策略、预算、进度和结果。候选审阅左右对照源文与替换文，并提供采纳、部分选区、丢弃和重新生成。外部修改保留本地草稿并提供比较入口。

使用明确的任务状态：

| 状态 | 含义 | 可执行的下一步 |
|---|---|---|
| 就绪 | 已选择目标和上下文 | 启动、编辑任务或取消 |
| 运行中 | 原生任务正在执行 | 观察或请求取消 |
| 等待作者 | 重大选择或缺失来源阻止继续 | 提供输入、缩小范围或丢弃 |
| 候选 | 有版本绑定的结果等待决定 | 比较、采纳、编辑或丢弃 |
| 已提交 | 准确授权的文档版本已保存 | 查看、续写或启动新任务 |
| 失败 | 没有有效提交就停止 | 查看诊断、重试缺失工作或丢弃 |

工作台只保存任务和产物引用。对话历史、模型选择、作业状态、subagent、Team 和取消记录由 DSH 负责。刷新、Session 切换和第二窗口必须能从这些引用恢复抽屉，且不能覆盖草稿。

<a id="delivery-sequence"></a>
## 交付顺序

先完成小说引擎和一条纵向闭环，再增加 Team 或广泛自动化。每个阶段都有可观察的产品结果和窄范围技术门槛。

| 阶段 | 交付物 | 证据 |
|---|---|---|
| 0. 引擎与适配边界 | 定义产物 schema、来源、任务契约和 DSH 适配接口 | 引擎可脱离 DSH 测试；隔离 DSH 运行显示实际工具范围、取消和终态 |
| 1. 安全编辑闭环 | 任务抽屉、上下文预览、候选差异、CAS 提交和丢弃 | 候选不改正文；旧版本被拒绝；采纳保留历史 |
| 2. 故事记账 | 设定圣经、当前单元细纲、章节摘要和账本提案 | 已提交章节产出有来源的提案；被拒绝的提取不改变权威事实 |
| 3. 有界续写 | 场景或章节流水线、检查点、审稿和交接记录 | 恢复不会重复已提交单元，也不会静默扩大范围 |
| 4. 批量与 Team | 串行多单元 workflow 和明确选择的 Team 研究 | 单元失败会停止后续；Team 产物归属清楚且无写入绕过 |
| 5. 安装与体验 | 安装包、浏览器行为、导入导出和写作对照 | 功能证据与文学质量证据分开报告 |

首批验收刻意保持小范围：一句话开书、候选场景、选区改写、下一章、旧源拒绝、外部编辑冲突、取消、刷新恢复和已有稿件接入。深浅色、窄窗口、键盘操作、中英文文案和隔离 `DSH_HOME` 仍属于浏览器验证。

文学质量另用相同模型和相近预算评估新开场、续写和局部修改。比较连续性、作者保留文本、干预次数、延迟和 token 使用；不把观察结果变成自动验收分数。

<a id="open-questions-and-evidence"></a>
## 待验证问题与依据

当前仓库已经具备文件发现、编辑缓冲、版本保存和 story Skill 的原生接入基础。本设计依赖这些基础，并把新增工作收敛到任务授权、候选持久化和可恢复编排。

实现前用隔离 DSH 实验回答：

- 作品服务能否对原生 workflow 子会话和具备 shell 能力的工具强制写入策略？
- 进程重启后，哪些原生作业和 Session 记录足以恢复已取消任务？
- 作者在支持的项目范围内移动或重命名文档后，任务引用如何保持有效？
- 支持顺序和历史的最小索引格式是什么，怎样避免它变成第二套正文数据库？

前一版研究仍可作为设计输入：作品状态应独立于聊天，显式材料应优先于推断记忆，候选应可比较。但它不能证明固定配额、强制闸门或新插件边界是合理的。
