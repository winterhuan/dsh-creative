# 审查流程

## 范围与材料

读取待审原文和相关设定、细纲、追踪状态。用当前项目与用户指令确定范围，不将整个工作区默认为小说。平台来自用户或本书 `目标平台` 字段；`.active-book` 仅辅助定位书名。

单章评审可直接读取整章。多章/整卷分批，路径与范围传给执行者，不向每个角色复制整本正文。仅在需要判断矛盾时检索更早的事实、核心角色快照和伏笔当前行；区分作者真相、读者已知与大纲未来计划。

作者记忆如存在，按 [作者习惯](../project/author-memory.md) 查询相关 active 条目，帮助解释意图，不降低事实标准或自动学习审查结论。

## 只读检查与评审

1. 根据 `story-review` 的路由选一次合适的评审：普通审稿默认主会话，正式章节优先由 `story-architect` 完成读者价值与事实连续性。特殊疑点才追加专门核查，不例行再走一套完整评审。
2. 长篇写作已经对相同正文执行 `storyctl.py chapter check` 时直接使用结果；未执行时，本地正文可运行以下只读预检，代码路径基于 DSH 资源目录：

   ```text
   node {资源基目录}/scripts/normalize-punctuation.js --check --project {项目根} {正文文件...}
   node {资源基目录}/scripts/check-ai-patterns.js --check --fail-on=blocking {正文文件...}
   node {资源基目录}/scripts/check-degeneration.js --check {正文文件...}
   ```

   同位置建议去重。AI 模式与标点仅作 advisory，不要求清零；退化检查的复读、截断或工程词泄漏按实际影响列 S1/S2。引号和停顿尊重项目与人物语气，不能把省略号或破折号本身当缺陷。工具失败标明未完成，不作为通过。
3. 对照所选平台或通用标准读正文，核查承诺、阻碍、选择、变化、兑现、后续期待，以及事实与因果。低压章可以靠关系变化、阶段收益或未解问题成立，不硬添高潮、反转或代价。技法只帮助解释具体损害，不能转成词频、事件数或段落比例门禁。
4. 输出带原文行号与引句的问题，按严重度排序；没有证据的判断列为缺口。涉及事实的 `fix` 说明需统一的来源或需要裁定的问题，不代写文学剧情。外部史实无法查证时标注未核实。
5. 章节提交时再按 [读者价值证据](reader-value.md) 返回 JSON；由写作流程提交，审查不修正文或追踪。正文变更后重新评审，未变更不重复。

委派 prompt 只需要项目与原文路径、审查范围、相关事实来源、所选标准的简要要求、统一问题字段和证据格式。执行者使用原生 `read` 获取资源；不把技能全文与多个重复 rubric 拼进 prompt。记录实际执行角色、模型与失败原因，不把部分结果冒充用户要求的全部范围。

## 分批连续性

跨两批及以上时，用 `{项目根}/.story-review/state.md` 保存完整审查范围、已完成范围、下一批及未解决问题摘要（`location / issue / 预计核查或兑现范围`）。每批完成后以同目录临时文件 + rename 原子重写；下一批先读它并接续相关未解决项。

同一项目只维护一个未完成批次计划；新范围会覆盖未完成进度时先说明并确认。续接状态丢失、损坏或请求超出既定范围时报告差异，不猜测旧结论。非分批审查不创建状态文件。

如果靠前批次发现了会影响已审靠后范围的新事实或开放项，只标出具体受影响范围并建议定点复审，不自动重跑整本。审查发现遗漏追踪事实时，报告来源和所属章，由 `story-write` 通过修订事务处理；审查进度文件不承担小说事实追踪。

## 报告

报告包含结论、实际范围、执行者与模型（能确认时）、标准来源、按 S1–S4 排序的问题、证据不足项及建议。每项使用以下字段；位置沿用原始文件行号。

```yaml
- severity: S1 | S2 | S3 | S4
  category: structure | character | prose | consistency | platform | factual | format | causal | rule_boundary
  location: 文件路径:行号
  evidence: 逐字引句或可复核的事实来源
  issue: 问题及影响
  fix: 可执行的修改方向
```

多个执行者有分歧时列出证据与未决点；没有问题时给出已检查范围和限制，不强造发现。
