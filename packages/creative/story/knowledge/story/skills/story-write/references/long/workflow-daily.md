# 长篇串行续写

用于用户明确要求日更、续写或指定章节范围；裸调用 `story-write` 只展示项目状态。默认未指定数量的续写写一章；明确日更但未给数量时本轮写两章。用户指定范围时按该范围串行完成，可分批汇报，不擅自扩大范围，也不在正常推进中反复询问是否继续。

## 开始

运行 `node {CLI} project check --workspace {工作区} --book {作品名} --json`，从紧凑结果取得 `last_committed_chapter + 1` 与 `state_revision`，核对 `追踪/上下文.md` 当前进度。已有正文却无追踪状态时，先由 `story` 接入建立必要状态，不要求完整拆文。状态损坏按 [追踪事务](tracking-transaction.md) 修复。

将用户范围和已知约束传入每章准备；准备执行者读取卷级目标、当前剧情单元和已有细纲，确认信息边界、必要兑现及章尾停笔点。缺细纲时按 [中途补纲](workflow-setup.md#中途补纲) 创建并检查，不要求用户事先准备完整批次的细纲。已确认卷纲的实质变化应先处理，不以续写名义静默重规划。

## 逐章循环

明确选用 [原生 workflow](native-workflow.md) 时，每章顶层调用同一份模板，包含 Prepare 的检查、补纲与场景计划，确认业务结果为已验证的 `committed` 或 `already_committed` 后才推进。`needs_input` 时补充具体缺失事实或作者决定，再从 Prepare 重启同一章；`revision_limit`、`uncertain` 或运行失败时停止推进，不用 `pipeline` 并发连续章。

每章完整执行一次 [单章流程](workflow-chapter.md)：准备 → 正文 → 检查 → 读者价值评审 → 事务提交与验证。下一章依赖上章落盘正文和已提交追踪，不能并发写多章。上一章提交失败或长度仍待用户裁定时停止推进。

下一章开始只加载变化后的续写状态卡、上一章正文和本章材料。已经读过且未变化的题材/文风参考可复用；无对标原创用本书细纲与设定，不能在手动执行路径额外要求对标情绪或节奏文件。

### 定点查旧信息

1. 优先使用续写状态卡的核心角色与下一章承诺；每章准备另按 [写前事实](continuity-context.md) 分页检查全部到期伏笔，不把状态卡未展示的项当成不存在。
2. 缺项时按角色名读 `追踪/角色状态/{名}.md`，按伏笔 ID 检索 `追踪/伏笔.md`，按事实归属选择作者真相或读者已知时间线。
3. 需要历史原因再查相关逐章记录或一章原文；也可把同类问题合并交 `story-explorer` 定点查询。不得为获取一个状态加载所有历史记录。
4. 不确定的旧事实标记证据缺口，不能用聊天印象补成确定事实。核心角色快照应存在而缺失时走事务修复，不手写临时替代物。

### 事务语义

每章只提交对后续有用的结果、角色变化、伏笔变化、事实/揭示、约束和下一章承诺。需要复用的核心角色变化要带完整动态快照；一次性路人不强建快照。当前位置、活跃角色、长期约束和连续性风险提交完整当前值；固定七栏及容量要求见 [追踪事务](tracking-transaction.md)。

长期约束最多六条，新增溢出先合并语义或裁定，不静默删除。删除仍登记的上下文项或退役角色要用 `delta.retired_context_items` / `delta.retired_characters` 明确声明；只在 append 退役，revision 保留截至最后已写章的完整当前上下文。

## 批次收尾

每章的检查与事务已完成，批末只检查跨章新问题：标题冲突、重复兑现、因果断点及阶段漂移。无正文变更不重跑全批模式、标点、退化或完整评审；也不重复提交追踪。发现需改已提交章时按修订流程重评审、提交该章。

汇报实际完成范围、字数、未决问题与剩余授权范围。用户中断时保留已提交进度和未完成稿，下次从真实状态接续。不要为了收尾新建逐章过程日志或重复追踪文件。
