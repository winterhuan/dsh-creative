# 长篇单章正文

本流程负责一章的准备、正文、检查、评审和提交；[日更](workflow-daily.md) 只组织串行批次，不另做同一章的检查或事务。确定性操作使用当前 Skill 定位的 CLI，参考只从本 Skill 读取。

明确选用原生 workflow 的新章，确认工程与章号后直接按 [原生 workflow](native-workflow.md) 调用模板，由 Prepare 执行下方准备，再进入写作、审稿和提交；父会话不重复这些阶段。其局部审稿 JSON 用于流程分支，以下普通路径保留自然语言审稿。

## 1. 准备本章

普通路径由主会话准备；原生 workflow 由 Prepare 子 Agent 执行。

1. 按 [项目与对标](project-context.md) 确认工程，用 `node {CLI} project check --workspace {工作区} --book {作品名} --json` 取得章号与修订号，读取当前剧情单元、上一章正文和续写状态卡。先按章号定位细纲和正文，兼容已有补零与章名；只读取已存在的文件，不把缺失细纲当成写手的输入，不覆盖已存在章节。写正文前把本次实际读到的文件列给作者：`追踪/上下文.md`、角色状态、伏笔、时间线、细纲、上一章和拆文页，并带上 `check` 返回的 `state_revision`。清单只在会话里展示，不另存成文件，也不替代 JSON。
2. 运行 `node {CLI} outline check --json --workspace {工作区} --book {作品名} --chapter {N}`。缺细纲返回 `ok=false`、`outline.readable` 和待补建路径，由准备执行者按 [中途补纲](workflow-setup.md#中途补纲) 完成本章文件，再用同一命令复检。通过结构检查后核对七项语义是否具体：读者期待、主角目标、主要阻碍、关键选择、代价或后果、局部兑现、章尾问题。缺少选择或状态变化时先修纲；未知关键事项不能只填占位符后直接写正文。
3. 按 [写前事实](continuity-context.md) 用 `node {CLI} project query --workspace {工作区} --book {作品名} --kind foreshadow --filter due --chapter {N} --json` 读取全部到期页，翻页带同一修订号；准备无法覆盖剩余项时停止并说明缺口。结合卷纲处理本章应消费的约束，不能只看状态卡的 8 条活跃伏笔。用定点查询筛选角色状态、信息边界与下一章承诺；需要历史原因再读对应记录或原文。读 [长篇格式](long-format.md)；题材卡、自定义文风和外部对标仅加载本次相关材料。无对标原创直接使用本书规划，不触发“缺少对标模块”错误。
4. 将重复细纲要求合并成紧凑 `scene_execution_plan`：每场目标、阻碍、策略/选择、后果、结果与信息边界，并指向已批准情节点。正文可重排、合并、交织场景，不逐条复述提纲；不得新增独立主线、角色、承诺、反转或提前泄露未来真相。行动成本可以没有，不为填表硬造代价。

题材和主角代理权有疑问时按 [读者契约](reader-contract-and-progression.md) 核对因果权、结算权、期待债与终局储备。若本章会改变已确认卷纲或兑现归属，先处理该实质冲突；普通场景组织不需要反复确认。外部事实只在本章需要时查证。

## 2. 写正文

主会话执行，或按 [原生协作](../delegation.md) 委派实际的 `narrative-writer` Agent。委派输入包含项目与输出路径、细纲、必要状态、场景计划、字数范围、当前题材/文风约束及所选参考的来源；不复制整本拆文报告或未选中的素材。`narrative-writer` 子角色只写正文，不写追踪或签发批准；主会话直接写作时，仍须在正文完成后进入下一节的适合本次范围的审稿阶段，不把自审称为独立评审。

按批准情节点分成前后两组，在同一执行会话完成。委派时将CLI 绝对路径、Skill 目录和临时文件路径一起传入，由 `narrative-writer` 在同一次调用内自行计数并完成后组；父流程不等待中途产物后再回传，只有完整任务结果返回后才执行最终检查。主会话直接写作时自行执行同一步骤。前组写入临时文件后只运行一次：

```text
node {CLI} text count --checkpoint --file {前组临时文件} --target {字数目标} --chapter {N} --json
```

把机器返回的 `actual`、`remaining_user_range` 与剩余情节点交给写手。剩余情节点完成即停，不为字数新增情节、逐点分配配额或反复扩写。两组组合成 `正文/第NNN章_章名.md`，标题与细纲一致，不与已有章节混淆。

正文中的停顿、重复、短句、长句服从人物与场景。写作工程词只存在于材料与报告；标题之外不得把“本章、细纲、伏笔、读者”等定位词写进叙事，故事内人物真实讨论章节或读者身份时例外。

## 3. 一次检查与读者价值评审

```text
node {CLI} chapter check --workspace {工作区} --book {作品名} --chapter {N} --json
```

该命令已包含细纲、字数、退化、AI 模式、标点和照搬检查，不再单独重复运行这些脚本。检查或评审之后正文有变化才重新执行；`chapter commit` 自身对提交时的当前文件再次验证是提交保障，不能跳过。

| 结果 | 动作 |
|---|---|
| `outline_readiness.status=fail` | 补细纲中的具体缺项后再检查，不用正文反推未批准剧情 |
| `TOOL_UNAVAILABLE`、`TOOL_ERROR` 或 `invalid` | 修复执行环境/输入，报告检查未完成；不宣称通过，不因此自动重写正文 |
| blocking quality | 根据可复核的问题修受影响内容；新增独立剧情须回到已批准范围，不能靠增写另一个事件解决 |
| 带内且 quality pass | 进入读者价值评审 |
| `under` 且 quality pass | 展示 `accept-current-length / revise-outline-or-target / discard`，不自动补写；按用户选择执行 |
| `over` 且 quality pass | 可按 `compress-once` 给出的区间净删一次，不增加语义或改变契约；复检仍带外则展示上述三项 |

字数以 `visible_chars_v1` 和细纲目标为准；用户明确上下限优先，否则内部带 ±12%、用户带 ±15%。缺目标不猜测，欠长不自动扩写。模式、标点及检测分数只供复核，不要求清零；复读、截断等实际退化需修复，工具错误与文本缺陷分开处理。

按 `story-review` 阅读最终正文，指出有依据的问题和修改建议，不提交固定评审 JSON 或模型证明。重要的承诺、选择、连续性或可读性问题应先处理；低压章可以靠关系变化、阶段收益和微期待成立。按反馈局部修订，重新检查并复核受影响内容。

## 4. 提交一次完整事务

按 [追踪事务](tracking-transaction.md) 从最终正文构造 `delta`、完整当前 `context`、必要角色快照，使用最新 `state_revision` 作为 `expected_state_revision`；事务不手填 `wordcount`。只记录对未来有用的事实与承诺，不把质检统计、引用材料或未来计划混入当前状态。

```text
node {CLI} chapter commit --workspace {工作区} --book {作品名} --chapter {N} --input {逐章事务.json} --json
```

带外且用户明确接受自然长度时改用 `chapter accept-current-length`，同样要通过质量检查与读者价值评审。已提交章修订用 `mode=revision`，按 [修订流程](workflow-revision.md) 核对截至最后已写章的当前状态。

提交在锁内重读正文和目标，校验字数记录哈希与修订号并原子发布状态及派生视图。失败不推进下一章；写入失败保留原事务重跑，校验失败按报错修事务，状态已变化则重读重构。成功后运行一次 `node {CLI} project check --workspace {工作区} --book {作品名} --json`；按需保留审稿意见，可删除临时正文片段；机械提交成功不代表文学质量通过。正文、事实、摘要与实际执行方式向用户如实汇报。
