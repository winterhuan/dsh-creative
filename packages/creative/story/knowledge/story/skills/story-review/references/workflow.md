# 审查流程

## 范围与材料

项目根指已选定的 `{工作区}/{作品名称}/` 直接子目录，长短篇一致。读取本书待审原文和相关设定、细纲、追踪状态，用用户指令确定范围；需要保存报告时也放在本书目录。单章可直接读整章，多章分批；只在判断矛盾时检索更早事实，区分作者真相、读者已知与大纲未来计划。

作者记忆如存在，用 `memory query --workspace {工作区} --book {作品名} --json` 查询匹配 active 条目，只帮助解释意图，不降低事实标准。具体一致性疑点需要独立核查时委派加载 `story-review` 和本地 [核查员](roles/consistency-checker.md)，传工作区、作品、范围与材料。

## 检查与判断

已有同一正文的 `node {CLI} chapter check --workspace {工作区} --book {作品名} --chapter {N} --json` 结果时直接使用，不重复跑脚本；需要单独预检时按实际问题选择：

```text
node {CLI} text normalize --workspace {工作区} --book {作品名} --file {正文文件} --json
node {CLI} text check --workspace {工作区} --book {作品名} --file {正文文件} --json
```

AI 模式和标点只是复核线索，不能要求清零。复读、截断和占位符按实际损害处理；工具失败说明检查未完成，不能当成通过。

阅读正文，核查承诺、阻碍、选择、变化、兑现、后续期待，以及事实与因果。低压章可以靠关系变化、阶段收益或未解问题成立；不把事件数量、段落比例或技法偏好当成通用验收条件。无法查证的外部事实标注未核实。

## 反馈与续接

输出简短结论、实际范围、重要问题及原文位置或必要引句、修改建议和证据缺口，不强制 JSON、模型元数据或固定字段。没有问题时说明范围与限制；多个执行者有分歧时列证据和未决点。

多批审查在当前会话接续；Team 模式使用原生任务板记录已完成和待查范围，以消息交接发现，不另建强制审查状态文件。需要跨会话带走进度或用户要求交付时，保存一份普通 Markdown 说明实际范围、未解决问题和下一步；已有进度资料先读后续，不覆盖未完成工作。

出现影响已审内容的新事实时，标出受影响范围并定点复核，不自动重跑整本。审查不改正文或追踪；遗漏故事事实由写作流程核对后提交修订。章节修改后重读受影响部分，旧意见不能认证新文本；是否提交由主会话结合实际问题决定，脚本不认证文学质量。

## 章节 workflow 的来源核对

审稿前后运行 `node {CLI} chapter snapshot --workspace {工作区} --book {作品名} --chapter {N} --json`，比较正文、细纲字节哈希、文件版本和状态修订号。需要仅核对细纲时加 `--outline-only`。任何变化都停止沿用旧结论，交回当前身份及缺口；不临时导入私有模块计算身份，也不把自己填入的哈希当已验证结果。

任务要求结构化路由时返回 recommendation 与可读 review；普通审稿仍用自然报告。提交者随后独立锁内核验预期身份，审稿者不写追踪。

需要体裁问题速查时，长篇用 [章节问题](long-chapter-quality.md)，短篇用 [正文问题](short-prose-quality.md)；具体通用问题再查 [质量观察](review-quality.md)。这些列表帮助定位，不要求每次审稿全量读取或固定评分。
