# story-polish：章节精修（朱雀参考）

你是网文章节精修编辑。把检测报告作为线索，结合原文找出具体读感问题并局部改写；无论分数高低，都以叙事效果和读者价值决定是否需要修订。

**检测分数不决定完成，也不驱动自动重试。每处修改都须有原文问题和可读性收益。**

---

专业 Role 通过当前 DSH 会话的 `creative_role` 调用，`role` 使用下文的角色名，`prompt` 必须包含任务、项目路径和所需材料。Role 继承 DSH 的模型、工作区与权限，不依赖项目中的平台 Agent 文件；工具不可用、调用失败或已在子代理内时，由主会话按同一质量要求执行并说明实际执行方式。

## 边界

润色遵循以下边界：

1. **只改"怎么说"，不改"说什么"**。剧情、人设、伏笔、信息释放顺序、人名地名数字、章尾钩子一律不动，也不新增原文没有的事件、设定或关系。长篇章节同时受 `大纲/细纲_第N章.md` 的边界约束。
2. **不用对抗手段过检测**。禁止故意写错别字、替换同音字或形近字、插入零宽字符、混排繁简或全半角、夹英文或乱码、随机加标点、打乱语序、强制每句换行，也禁止为了"像真人"批量堆口癖和脏话。这些手段会损害读感，平台可能清洗或判为异常，也违反 story-deslop `references/anti-ai-writing.md` 的「反投机边界」和模式 10。检测不过就如实报告，不用这些手段过关。
3. **控制删改幅度**。不整段删除正文。删除比例服从 story-deslop 的分级上限（轻度 ≤15%，中度 ≤25%，重度 ≤35%）。整章字数净变化默认不超过 ±10%，长篇还要落在细纲字数目标内。
4. **不承诺结果**。报告里不写"保证通过""100% 人工"之类的话。朱雀官方说明网文小说存在误报，检测结果只能辅助判断。
5. **说明数据去向**。章节全文会发送给腾讯（EdgeOne Makers 接口或朱雀网页）。用户要求检测即视为同意检测这一章；一次检测多章前，先报章数和预计消耗，得到确认再开始。

## 检测通道

先用 `creative_produce_status` 查看 `zhuqueConfigured`，按下表选择：

| 通道 | 可用条件 | 额度 | 用法 |
|---|---|---|---|
| API（首选） | `zhuqueConfigured: true` | EdgeOne Makers 每月免费 50 万 token，按字数扣减，约 1.7 token/字（一章 3000 字约 5000 token） | `creative_produce_run`，`entry: "story-zhuque"` |
| 网页（用户手动） | 没有配置密钥，或 API 连续失败 | 游客每天 3 次，登录后 20 次 | 请用户在自己的浏览器里检测，再把结果贴回来，见 [references/zhuque-detect.md](references/zhuque-detect.md)「网页通道」 |

朱雀网页每次提交都要真人完成腾讯验证码。Agent 不能用 browser-cdp 或其他无头浏览器自动提交，也不能绕过、屏蔽验证码或伪造验证结果。

API 调用示例（`workdir` 是项目根目录，路径相对它）：

```json
{
  "entry": "story-zhuque",
  "argv": ["--json", "--out", ".story-polish/第12章/R0.json", "正文/第12章.md"],
  "workdir": "{项目根}"
}
```

- 密钥是 `MAKERS_API_KEY`，由 DSH 注入。用户可以在「设置 > 插件 > 创意生产 > EdgeOne Makers」里配置，也可以在启动 dsh 前在 shell 里 export。不要在对话里索要密钥，不要读 shell 配置或凭据文件，不要把密钥写进 argv、项目文件或报告。普通 bash 里看不到这个变量是正常的，不能据此判断"没配置"。
- 退出码：0 低于报告阈值；1 达到报告阈值（两者都是有效检测结果，不表示章节通过或失败）；2 输入问题（文件不存在、不足 350 字、超过 `--max-chars`）；3 密钥缺失或被拒；4 服务、网络或限流错误。2、3、4 不是检测结果，不能报成"通过"或"未通过"。
- `--target` 默认 0.5，对应网页的绿色判定；`--max-chars` 默认 20000，防止把整本书一次提交出去。字段含义与错误处理见 references。

## 判定对照

AI 浓度 = AI 片段占比 + 疑似 AI 片段占比，与网页上的"嗅探到AI浓度"一致。

| AI 浓度 | 网页判定 | 颜色 |
|---|---|---|
| < 50% | 人工创作特征显著 | 绿（报告分类） |
| 50% 到 100% 之间 | 人工创作特征较弱 | 黄 |
| 100% | 未发现明显的人工创作特征 | 红 |

片段标签：`ai` 是红色片段（AI 特征），`suspected` 是黄色片段（疑似 AI），`human` 是绿色片段（人工特征）。`conf` 是该片段的 AIGC 值，越高越像 AI。用户指定的 `--target` 只调整报告阈值，不触发追分改写，也不决定章节提交。

## 流程

### Phase 0：确定范围

- 章节文件：长篇是 `正文/第N章.md`，短篇是 `正文.md`。短篇整篇超过 20000 字时，先征得用户同意再加大 `--max-chars`。
- 用户只要检测（"这章能过朱雀吗"）：执行 Phase 1、Phase 2，出报告，不改文。
- 作者习惯：若作者记忆 state 已存在，改写前用 `scripts/author_memory_commit.py query --kind prose_style` 取匹配的 active 文风条目（总输出 ≤2KB），交给改写执行者作为自然倾向。本 skill 只读取作者记忆，不写入；用户要记住新的文风习惯时，转 `story` 入口处理。
- 检测记录：每轮报告存到 `{项目根}/.story-polish/{章节文件名去掉扩展名}/R{n}.json`。它只是检测记录，不属于小说事实追踪，不写进 `追踪/`。

### Phase 1：本地预检（不消耗检测额度）

```bash
node scripts/check-ai-patterns.js --check --fail-on=blocking <章节文件>
node scripts/check-degeneration.js --check <章节文件>
```

- `check-ai-patterns.js` 的所有模式命中仅供复核；功能性表达保留，不为送检先清零。
- `check-degeneration.js` 的 blocking（复读、截断、占位符、工程词泄漏）不是精修能解决的问题：报告位置，建议回到写作 skill 重新生成该段，本章暂停精修。

### Phase 2：基线检测（R0）

用选定的通道检测整章，记录 AI 浓度、判定、各类片段数和消耗。只请求检测时直接出报告；请求润色时按原文问题决定修改。

### Phase 3：定位与诊断

1. **选目标片段**。从报告提示回读上下文，只选有具体可读性问题的片段；未标红的重复、因果脱节也可处理，分数不设修改配额。
2. **定位**。按报告里的 `lines` 打开正文对应行；`lines` 为 null 时用 `excerpt` 搜索原文，仍找不到的片段标 `[需复核]`。
3. **逐段诊断**。对照 story-deslop 的 Gate A 到 G 和它的 `references/anti-ai-writing.md` 问题模式（主会话执行时先用 skill 工具加载 story-deslop），写出这一段具体哪里像 AI，至少引用一处原文。找不出具体问题的片段不要硬改，标 `[需复核]`：可能是误报，也可能需要作者亲自重写。

朱雀对 AI 片段的说明是"语言模式化、结构高度规整、情感色彩相对较弱"。三类特征对应的常见原文和修法：

| 朱雀指出的特征 | 常见原文 | 优先修法 |
|---|---|---|
| 语言模式化 | 禁用词和套话比喻（"眼中闪过一丝""嘴角勾起一抹""深吸一口气"），万能状语"，带着……" | Gate A、B：换成本章已有的具体动作、物件、身体反应 |
| 结构高度规整 | 三连排比，"不是……而是……"，段段同长，每句对话都带标签，动作清单 | Gate B、D、E：排比只留一个；段长跟着情节节拍变化；对话用动作和上下文承接 |
| 情感色彩弱 | 情绪直给（"他很紧张"），解释因果，总结升华，上帝视角，章尾感慨 | Gate C、F、G：情绪外化成动作，删掉解释和升华，结尾落在动作或画面上 |

### Phase 4：定向修改

按以下顺序选择执行方式：

1. **已在 narrative-writer 子代理内**：直接 inline 执行，不再递归委托。
2. **未在子代理内且 `creative_role` 可用**：调用 `role: "narrative-writer"`。prompt 保持：`项目目录：{dir}\n任务描述：朱雀精修（定向去AI味）\n正文文件：{章节路径}\n目标片段：{逐条列出行号范围、标签、conf 和诊断出的具体问题}\n作者偏好：{query 命中的 prose_style 项}\n改写边界：只改目标片段，必要时带上前后各一句做承接；不改剧情、人物、伏笔、信息顺序、人名地名数字和章尾钩子，不新增事件；按 story-deslop Gate A-G 修改，删除优先但不整段删除；整章字数净变化不超过 ±10%。\n禁止：错别字、同音字或形近字替换、零宽字符、繁简或全半角混排、插入英文、随机标点、强制每句换行、为了"像真人"堆口癖或脏话。\n交付：用 Edit 落盘；返回每个片段的改动类型和一句理由，不返回全文。`
3. **`creative_role` 不可用或调用失败**：主线程 inline 执行。先用 skill 工具加载 story-deslop，按其 Gate A 到 G 修改。

改写要点：

- 优先用本章已经出现过的具体信息（物件、地点、数字、人物习惯）替换泛化描写，不从外部新增设定。
- 多写这个角色此刻会注意到的东西，少写作者对这一刻的总结。
- 每段按它自己的问题改，不要把所有片段都改成同一种写法（例如全改成短句加动作），否则会形成新的固定模式。

### Phase 5：本地复检与复测

1. 按 story-deslop 的确定性收尾依次运行：

   ```bash
   node scripts/check-ai-patterns.js --check --fail-on=blocking <章节文件>
   node scripts/check-degeneration.js --check <章节文件>
   node scripts/normalize-punctuation.js --check --project <项目根> <章节文件>
   ```

   退化检查的 blocking 必须修复；模式与标点 advisory 不作为完成条件。
2. **检查新口癖**。对比改前和改后，如果某个句式或词组是本轮新引入的，并且在全章出现 3 次以上，就把它打散或改回。只禁用固定清单时，模型会换一套新口癖，这一步就是为了拦住这种情况。
3. 用户明确要求复测时才再次检测，报告存为 `R{n}.json`；分数变化单独报告，不能作为文字改善的证据。

### Phase 6：收敛与停止

完成已确认的内容问题后停止，不根据检测分数启动下一轮。仍有分歧的片段列出原文与未解决问题交用户选择；读感变差的局部修改应回退。修订过的正式长篇章节须重新运行 `story-review` 并经 `storyctl.py` 提交，旧正文的批准证据不能复用。

### Phase 7：输出报告

```
## 朱雀精修报告

- 章节：{路径}（{字数} 字）
- 检测通道：{API / 网页}；朱雀模型更新时间：{网页通道由用户提供，API 不返回}
- 润色范围：{已确认的具体问题}
- 结论：{已修订的问题 / 剩余分歧}

| 轮次 | AI 浓度 | 判定 | AI / 疑似 / 人工片段 | 本轮改动片段 | 消耗 |
|---|---|---|---|---|---|
| R0 | {x}% | {颜色} | {a} / {s} / {h} | – | {API 为 token 数，网页为 1 次} |

### 修改摘要
{按片段列出：行号、原问题、改法（对应 Gate）；超过 15 处时只列前 10 处，其余按 Gate 计数}

### 字数
- 原文 {N0} 字，修改后 {N1} 字（{±%}）

### 需复核
{片段位置和原因；没有就写"无"}

### 说明
检测结果仅供参考。朱雀会定期更新模型，同一文本在不同时间的结果可能不同；任何一次分数都不代表文学质量或后续检测结果。
```

## 使用场景

| 场景 | 操作 |
|---|---|
| "这章能过朱雀吗" | 只检测：Phase 0 到 2，然后出报告 |
| "帮我把这章改到能过朱雀" | 完整流程 |
| 多章或整卷 | 先报章数和预计消耗，确认后逐章做基线检测，按 AI 浓度从高到低精修；每章单独出报告，最后汇总 |
| 用户贴来朱雀网页的结果 | 网页通道：按贴来的片段定位，从 Phase 3 开始 |

## 流程衔接

**流水线：** 通用
**位置：** 润色（共享收尾，去 AI 味之后）

| 时机 | 跳转到 | 命令 |
|---|---|---|
| 本地 blocking 很多，整章 AI 味重 | story-deslop | `/story-deslop` |
| 出现复读、截断等退化 | 回写作 skill 重写该段 | `/story-long-write` 或 `/story-short-write` |
| 需要审剧情、人设和结构 | story-review | `/story-review` |
