# NovelToGame 总入口

先检查用户请求、原著与已有工程，确定本次交付是原著取证、设计建议还是可玩游戏。保留已批准决定，不为补齐阶段重做已有工作。项目位于 `game-adaptations/<project>/`。

## 按任务推进

- 接入原著或开始改编：按 `references/intake-method.md` 起草 `PRODUCT_BRIEF.md`，只澄清会改变目标、输出或投入的歧义。
- 分析小说的改编基础：按 `references/analysis/workflow.md` 读取目标范围并生成 `analysis/SOURCE_BIBLE.md`。先确定改编范围，只有要求全书分析时才覆盖全书；选段结果不能冒充全书结论。来源事实与游戏发明分开。
- 选择玩法、设计系统/关卡或美术：加载 `game-design`；已选方向直接细化，不强制重新比较多个概念。
- 实现已批准设计或验证最大风险：加载 `game-build`。白盒按风险选形态；仅在需要验证不确定性时先做，不重复制造相同候选。
- 验证实际构建：加载 `game-qa`。修复后重跑受影响验证，不能通过改预期来掩盖失败。

`quick` 使用明确假设推进用户要求的范围；`director` 在有实质分歧的设计选择处给推荐并等待裁定；`resume` 对照 `_progress.md` 与真实产物继续缺失工作。只要规划或分析时停在相应产物，不自动构建。

详细产物与恢复边界见 `references/pipeline-contract.md`。参考路径相对 DSH 给出的资源基目录，用原生 `read` 按需读取，不预加载所有阶段。

## 不可跳过的边界

- 从原著或小说工程取材，保留来源和必要引句，不从短剧剧本推导整套游戏系统。bridge 提供独立随包的原著导出、索引与谱系脚本。
- brief 锁定目标平台、实际交付物、运行时、范围、语言、内容尺度与 `targetFinish`；改变已批准边界需明确裁定。工具链缺失不等于授权换成网页。
- 原作必须影响玩家动作、选择和世界反馈；生成模型可提出动作候选，规则器才能提交状态、知识和不可逆承诺。
- `targetFinish` 描述成色，不改变最小 QA。web 游戏以 `build/app/index.html` 为入口，使用本地相对资源与 Studio 的预览策略。
- `qa/verification.json` 是唯一机器 QA 事实源；真实启动、渲染、输入、核心循环、结果、重开六项全部 PASS 才能声明该候选通过。缺工具或证据是 NOT_RUN/FAIL，不能手写 PASS。
- 当前认证驱动只验证 Chrome 浏览器构建；其他目标要单独交付与说明未覆盖项，不能用浏览器替代结果证明目标平台通过。机器 QA 不证明趣味、平衡、权利或发布质量。
