# 短篇规划、正文与交付

按请求交付构思、设定/小节大纲或完整正文；用户只要规划时不自动写正文。参考按当前问题读取，不要求开工前把基础资料和题材包全部读到 EOF；已读且未变化的内容可复用。

## 1. 确定范围

确认故事核心情绪、主角、冲突、平台和用户字数要求；请求中已有的信息不重复问。用户没有方向时由 `story` 做选题建议。已有标准短篇项目直接续作；原始 TXT/Markdown 需要整理时走 `story` 的文本接入，不先强制全书分析。

用户明确上下限时原样保留；只给单值时默认目标的 95%–105%；未给字数时以 8000–20000 字作为初始范围。小节数量按故事设计与用户要求确定，不设统一每节字数、事件数或对话占比。

项目目录固定为 `{工作区}/{作品名称}/`，与长篇使用同一层级；在其中使用 `设定.md`、`小节大纲.md`、`正文.md`；外部对标只引用本次有用的分析，不把本书分析当对标，也不为无对标作品制造依赖。

## 2. 规划

根据当前任务选择一个 [题材包](genre-styles/) 或 [题材速查](genre-writing-formulas.md)；需要设计反派时读 [反派与揭露](villain-and-reveal.md)，反转问题读 [信息差](../methods/short-reversal.md)，投稿要求读 [投稿](submission-craft.md)。未用的参考不加载。

`设定.md` 写入核心梗概、角色目标与关系、冲突走向、结局落点及以下 `## Phase 2 设计校验` 字段：

- `目标平台`、`目标字数`：本篇真实平台和范围。
- `题材参考`：实际查阅的 `references/short/genre-styles/{题材}.md`，冷门题材用 `references/short/genre-writing-formulas.md`。
- `核心招式`：从所选资料提炼本篇适用的方法（至少一项），以分号分隔；它们是设计选择，不是正文次数配额。
- `反派设计`：有反派时写身份、动机、作恶方式、致命弱点、报应；不适用时写 `反派设计：不适用（原因）`，不为模板硬加反派。
- `反转类型` 与 `反转位置`：有反转写 `反转位置：第 X 节 ÷ 共 Y 节 = Z%`，仅校对节次和分配，不以百分比作为质量线；无反转写 `反转类型：无反转` 和 `反转位置：不适用（原因）`。
- `付费点`：仅付费交付写 `付费点：第 N 节末`，并在该节大纲的承接/钩子格注明；免费或未采用付费平台写 `付费点：不适用（原因）`。

`小节大纲.md` 每节一行，保留供确定性检查读取的 12 列：

```text
| 结构段/五段功能 | 主事件 | 情节推进 | 情绪 | 人物/关系变化 | 因果/逻辑链 | 读者新获知什么 | 结尾承接/钩子 | 伏笔/物件 | 场景形态 | 对白作用 | 目标字数 |
```

表头后加 Markdown 分隔行。情节推进写具体发生的事，用 `{对话/冲突/伏笔/回忆/发现/递进}` 中适用标签标注，先后关系用 `->` 连接；一个有意义的动作链即可，不为数量补情节。因果写原因、行动、结果与后果，关系未变可写本节实际改变的信息、风险、资源或决定。结尾节写完整落点，不硬留下一集悬念。对白无必要时注明实际推进方式，不硬添话轮。

反转检查错误解释是否影响了人物决定、揭示是否有可回看的依据、揭示后是否产生行动或结算；不要求固定假线索数量、三条真线索或读者绝对猜不到。道具可选，使用时按意义变化检查铺垫与回收，不要求三次出现或固定节距。

```text
node {CLI} short plan-check --workspace {工作区} --book {作品名} --json
```

该命令只检查设计文件可消费性，不能代替质量判断。失败按 `repair_scope` 修点名字段后再检，不无目标重写全部内容，也不为通过字段伪造已确认事实。通过后按用户请求停在规划或进入正文。

## 3. 按场景写正文

写前读 [短篇格式](short-format.md)，具体写法有疑问再读 [短篇技法](short-craft.md) 或题材卡。按大纲将情节点演成有选择、有后果的场景，可以合并或交织，不能逐行扩成模板段落。

每节的行动、证据、对话、等待或关系选择应改变有意义的状态；篇幅由这个变化决定。段落长短、标点和情绪词频服从人物与阅读效果，保留功能性停顿、重复和口语，不设全篇词数配额或“前百字三个事件”。

直接保存 `正文.md`，用户只请求某节时只写该范围。全文请求可分批完成，但保持同一个故事状态，不并发写有先后依赖的场景。需要中途计数时使用同一非空白字符口径，不靠模型估算，更不为拉齐节长新增事件。

## 4. 检查与交付

先检查读者承诺、主角选择、因果、状态变化与结局兑现；需要独立审稿时用 `story-review` 一次完成。短篇结尾以整篇承诺的兑现与余韵为准，不套用长篇“下一章问题”。局部文字问题按 `story-polish` 修复，不默认提交到外部检测服务。

只交付指定小节时，回读该节和前后衔接，只对已写范围做内容与退化检查，报告局部字数及未完成范围；不运行全文总字数或总节数检查，不为此补写用户未要求的小节。

全文已完成且用户要求整篇交付时，执行一次只读预检与交付检查：

```text
node {CLI} text check --workspace {工作区} --book {作品名} --file {作品目录}/正文.md --json
node {CLI} text normalize --workspace {工作区} --book {作品名} --file {作品目录}/正文.md --json
node {CLI} short delivery-check --workspace {工作区} --book {作品名} --min-chars {MIN} --max-chars {MAX} --sections {N} --json
```

模式与标点命中仅供复核，不要求清零；实际复读、截断、工程词泄漏要修复。交付检查核对用户字数、节数与排版形状，失败按明确原因最小修复，文本变更后重跑受影响检查；工具不可用或运行失败不声称通过。字数不足先查已批准内容是否遗漏，已完成则说明自然长度并让用户选择接受或改规划，不为凑数强加剧情。

交付实际文件、机器字数与未决问题；不把检查报告、标签或方法说明混进小说正文。
